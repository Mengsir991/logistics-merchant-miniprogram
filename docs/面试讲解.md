# 面试讲解稿 · 发货助手（物流商家端小程序）

> 用途：面试时讲这个项目，以及被追问时的答法。所有数字与代码位置均已对照仓库核对。

---

## 一、两个版本的自述

### 30 秒版（开场自我介绍后带出项目时用）

> 我做过一个物流商家端的发货打单小程序，微信原生加云开发。核心链路是：商家批量导入订单 → 向快递服务商取号拿电子面单 → 打印面单 → 回传状态 → 查轨迹。
>
> 比较有挑战的是三块：一是批量导入的幂等和校验，二是面单服务商的解耦，三是打印环节——小程序没法直接驱动打印机，这块我做了取舍。

### 3 分钟版（面试官说"讲讲这个项目"）

按 **背景 → 难点 → 方案 → 结果 → 反思** 讲：

1. **背景**：电商商家每天几十上百单，逐单在快递系统里录入不现实。所以要的是"一次导入一批、批量取号、批量打单"。
2. **难点**：
   - 导入必须幂等——同一份 Excel 手抖导两次，不能变成两倍单量
   - 电子面单不是微信一家的能力，要对接快递公司，每家参数都不一样
   - 小程序不能直接调打印机
3. **方案**：
   - 幂等用「商家 ID + 订单号」唯一索引 + 服务端查重双保险
   - 面单做成适配层，三家服务商的差异关在一个文件里
   - 打印先落「保存图片 + 蓝牙」两条路，生产主推云打印机
4. **结果**：6 个页面 + 2 个云函数，前端全流程跑通，面单这块目前是 mock，等签约后接真实接口。
5. **反思**：最后一块我说一下我踩的坑（下面第五节第 5 条），这个比顺利的部分更有价值。

> ⚠️ 别说"我做了一个完整的物流系统"。说"商家端打单工具，面单是 mock 的"。面试官一旦发现你吹，前面全塌。

## 二、架构分层

```
页面层   6 个页面（主包 3 + 分包 3）
  ↓  只做渲染和交互，不直接调云函数
服务层   services/order.js  统一封装 8 个 action
  ↓
工具层   utils/cloud.js（统一错误处理） / parse-import.js（解析） / ble-printer.js
  ↓  wx.cloud.callFunction
云函数层 auth（登录鉴权） + orderApi（运单主接口，8 个 action）
  ↓
数据层   merchants / orders / import_batches
```

**为什么分这么多层？** 页面里不出现 `wx.cloud.callFunction`，全部走 `services/order.js`。好处是云函数改名、加统一重试、加埋点，只改一个文件。同理 `utils/cloud.js` 统一把 `{code, msg, data}` 协议转成 `throw Error`，页面里只需要 `try/catch` 一次。

## 三、六个技术决策（面试官最爱问"为什么"）

### 1. 为什么选原生，不用 uni-app / Taro

| 维度 | 原生 | uni-app / Taro |
|---|---|---|
| 构建链路 | 无，IDE 直开 | 需要 CLI/HBuilderX |
| 审核风险 | 最低 | 偶有兼容问题 |
| 多端能力 | 只有小程序 | 可出 H5/App |

**答法**：需求明确只做小程序，多端能力在这里是负资产——多一层构建就多一层调试成本。如果后续要出 H5 给商家在电脑上用，我再上 uni-app，那时多端的收益才成立。

### 2. 为什么用云开发，不用自建服务器

- 云开发：不用买服务器、不用域名备案、不用配 HTTPS 证书，小微商家场景起步最快
- 自建：可控、可迁移、能跑长任务

**答法**：这是**规模权衡**。日均几百单用云开发成本几乎为零；但如果单量上到几万、需要跑复杂报表和定时对账，云开发的限制（单次查询 100 条、云函数最长 60 秒）就会卡住，那时候要迁。我在 README 里写明了这个迁移边界，不是没想到。

> 加分点：主动说清楚技术选型的失效条件，比一味夸好更有说服力。

### 3. 为什么要分包

主包只放 3 个 tabBar 页面（工作台、运单列表、我的），批量导入、运单详情、打单放进 `pagesShip` 分包，并配 `preloadRule` 在进入工作台时预下载。

**答法**：小程序主包上限 2MB，超了直接传不上去。更重要是首屏——主包越小，冷启动越快。打单页有大量 canvas 绘制逻辑，天然适合分包。

### 4. 面单服务商为什么做成适配层

`cloudfunctions/orderApi/lib/delivery.js` 只暴露三个函数：

```js
createWaybill({ order, merchant })   // 取号
cancelWaybill({ order })             // 作废
queryTrace({ order })                // 查轨迹
```

**答法**：这是典型的**依赖倒置**——上层业务只依赖抽象接口，具体实现（微信物流助手 / 快递鸟 / 各家直连）通过 `DELIVERY_MODE` 环境变量切换。换服务商不改业务代码。

这里我刻意**没有**把任何一家的接口参数写死。因为各家签名算法和编码字典会变，凭记忆写出来的参数大概率是错的，等于给后面埋雷。我宁可留一个明确的 `throw new Error('未实现')`，让人知道这里要按官方文档填。

> 这个答法体现的是"知道自己不知道"，面试官通常吃这套。

### 5. 身份鉴权怎么做的

**所有 action 的 openid 都从服务端取，前端传什么都不信**：

```js
const { OPENID } = cloud.getWXContext();   // 云函数里
// 每条查询都带 openid 条件
db.collection('orders').where({ _id: id, openid })
```

**答法**：小程序前端代码是明文的，用户可以随便改请求参数。如果信前端传的 `merchantId`，改个数字就能看别人家的运单。所以身份必须由服务端从上下文里认——这也是为什么我把 `merchantId` 从前端请求参数里彻底删掉了。

### 6. 打印方案怎么取舍的

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 保存图片到相册 | 零硬件依赖，最稳 | 要额外一步打印 | **主推** |
| BLE 蓝牙打印 | 一步到位 | 位图数据 100KB+，单张数秒到数十秒 | 实验性 |
| 服务商云打印机 | 最快最稳 | 要买设备 | 生产推荐 |

**答法**：小程序只能走 BLE，走不了经典蓝牙 SPP，所以很多老打印机根本连不上。而且位图打印要把整张面单按行打包成 ESC/POS 光栅指令，分包写入很慢。我的判断是：**打印这件事不该在小程序里硬扛**，生产环境应该用服务商的云打印机，HTTP 下发，秒出。小程序做好"生成面单数据"就够了。

## 四、五个可以深挖的实现细节（面试官问"具体怎么做的"时讲）

### 1. 批量导入的幂等（P0 难点）

三层防护：

| 层 | 做法 | 防的是什么 |
|---|---|---|
| 表内去重 | 用 `Set` 记住本次已出现的订单号 | 同一个 Excel 里重复行 |
| 库内去重 | 按 `merchantId + shopOrderNo` 查库 | 同一份文件导两次 |
| 数据库唯一索引 | `merchantId + shopOrderNo` 复合唯一索引 | 并发情况下的漏网之鱼 |

**为什么三层都要？** 前两层是应用层判断，中间有并发窗口——两个请求同时查到"不存在"就会都插入。唯一索引是最后兜底。这个顺序是应用层优化 + 数据库兜底的标准组合。

### 2. 批量写入的并发控制

```js
for (let i = 0; i < toInsert.length; i += 20) {
  await Promise.all(chunk.map(v => db.collection('orders').add(...)));
}
```

**答法**：200 条一次性 `Promise.all` 会把数据库连接打满，云函数容易报错；一条一条写又太慢会超时。20 条一批是压测出来的折中。同理，批量取消运单我是**串行**的——因为要调服务商接口，并发会触发对方限流。

> 一句话总结：**自己家数据库可以并发，调别人家接口要串行**。

### 3. 云函数超时这个坑

云函数默认超时 **3 秒**，导 200 单必然超时。部署后必须去控制台改成 20 秒。

**答法**：这个坑我第一次跑批量导入就撞上了，报的错跟业务逻辑完全无关，排查了半天。后来我把这条写进 README 的部署步骤第 5 步，加粗。**经验是：部署配置也是代码的一部分，得写进文档，不然换个人部署还会踩。**

### 4. 搜索 + 权限过滤的组合查询

关键词搜索要匹配 4 个字段（订单号、运单号、收件人、电话），同时必须限定 `openid`。写法：

```js
condition = _.and([
  { openid },
  _.or([{ shopOrderNo: reg }, { waybillNo: reg }, { 'receiver.name': reg }, { 'receiver.phone': reg }])
]);
```

另外正则里的特殊字符要转义：`kw.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')`，否则用户输入 `(` 会直接让查询报错。

### 5. 我踩的一个真 bug：分页页码

**现象**：运单列表上拉加载，出现重复数据。

**原因**：我最初写的是

```js
if (isAppend && res.hasMore) this.setData({ page: page + 1 });
```

首次加载走的是 `isAppend = false` 分支，页码停在 1 没递增；上拉时又请求第 1 页，于是重复。

**修复**：把页码递增放进同一个 `setData`，无条件按 `hasMore` 计算：

```js
this.setData({ list, page: res.hasMore ? page + 1 : page, ... });
```

**答法**（这段建议原样讲）：这个 bug 暴露了我一个思维习惯问题——我把"页码递增"当成了"翻页时的动作"，但它其实是"一次成功加载后的状态"。状态更新应该跟加载结果绑定，而不是跟触发方式绑定。

### 6. 跨页状态同步（tabBar 页不能带参数）

`wx.switchTab` 不支持 query 参数。工作台点"待打印"跳到运单列表，需要带上筛选状态。

**做法**：走 `globalData` 传标志位。

```js
// 工作台
app.globalData.presetStatus = 'pending_print';
wx.switchTab({ url: '/pages/order-list/order-list' });

// 运单列表 onShow
const preset = app.globalData.presetStatus;
if (preset) { app.globalData.presetStatus = ''; this.setData({ status: preset }, () => this.reload()); }
```

配套还有一个 `needRefreshOrders` 标志：批量导入完成后置位，运单列表 `onShow` 读到就强制刷新。因为 tabBar 页切回来时 `onLoad` 不会再执行。

## 五、高频追问 Q&A（12 条）

**Q1：这个项目你独立做的？哪部分最难？**
> 独立做的。最难的不是写页面，是**面单**。因为它不是一个纯技术问题——你没法靠写代码解决"必须和快递公司签约"这件事。我能做的是把这块隔离干净，让接入成本最低，同时不假装它能跑。

**Q2：面单是假的，那你这项目是不是没做完？**
> 是没做完，但不是不能做。取号需要商户资质和月结账号，这部分不是技术门槛。我的代码结构已经留好了接入点：`delivery.js` 换实现、环境变量配密钥，业务代码一行不用改。面试前我更在意的是**架构上别留死路**。

**Q3：为什么用 mock 而不是接快递鸟的免费测试接口？**
> 快递鸟测试接口也需要注册审核，而且返回的运单号是测试号，一样不能真实发货。用 mock 的好处是前端全流程可以跑通、可以演示，不受账号审核进度影响。

**Q4：云开发的数据安全性怎么保证？**
> 三层：① 数据库集合权限设为"仅创建者可读写"，前端不直连数据库；② 所有读写走云函数，openid 从 `getWXContext()` 取；③ 每条查询强制带 `openid` 条件，做不到"改个 id 看别人数据"。

**Q5：数据量大了怎么办？**
> 现在有 4 个索引：`openid+createdAt`、`status+createdAt`、`merchantId+shopOrderNo`（唯一）、`waybillNo`。列表分页 15 条。真到几十万单，要按月份分表或者迁出云开发——云开发单次查询上限 100 条，聚合能力也弱，做报表会很难受。

**Q6：小程序 2MB 上限你怎么控的？**
> 主包只放 3 个 tabBar 页面，重逻辑进分包的 `pagesShip`。另外开了 `lazyCodeLoading: requiredComponents`，只加载用到的组件。

**Q7：setData 有什么要注意的？**
> 只传变化的字段，用路径更新。比如勾选运单我是 `list[3].checked` 而不是整个 list 重设；批量填状态是用 `orders[2].status` 这种。列表 15 条看着不多，但如果整表重设，滚动时会有明显掉帧。

**Q8：onShow 里会不会重复请求？**
> 会。工作台我加了 30 秒节流：`if (this._lastLoad && Date.now() - this._lastLoad < 30000) return;`。但导入订单后必须能看到新数据，所以额外加了 `needRefreshDashboard` 标志位绕过节流——**缓存和实时性的矛盾，要用显式的失效信号解决，不能靠缩短缓存时间**。

**Q9：登录态怎么管的？**
> `app.ready()` 返回 Promise 并做缓存，多页面并发 `await app.ready()` 只会发一次云函数调用。失败时清空缓存允许重试。

**Q10：打印那块你写的 ESC/POS 指令，具体是什么？**
> 是 `GS v 0`（1D 76 30 00）光栅位图指令。结构是 8 字节头 + 位图数据：头里 2 字节是每行字节数、2 字节是行数，数据部分按行、按位打包，1 个 bit 一个点，超过 128 灰度算白。最后拼一个走纸 + 切纸指令（`1B 64 04` 和 `1D 56 42 00`）。
> 分包大小要按协商到的 MTU 减 3 字节算，未协商时用 20 字节，每包之间要留间隔，否则打印机会丢数据。

**Q11：如果让你重做一次，会改什么？**
> 三件事：① 导入解析做成 Web Worker 或者提前校验样例，现在 200 行同步解析在低端机上会卡一下；② 面单取号加任务队列，现在是前端逐单串行调，200 单要等很久；③ 状态机用常量表 + 校验函数统一管理，现在状态流转散在几个 action 里。

**Q12：这个项目有什么是你没想清楚的？**
> 权限模型。现在是"一人一号"，openid 就是商家身份。但真实场景是老板开号、几个员工一起打单，需要子账号和角色。这块我当时直接跳过了，因为想不清"员工离职后他打过的单归谁"，这是我目前的能力边界。

1. 工作台 → 说"这里是运营视角，今日单量、待打印、异常件"

## 九、面试前 10 分钟速记

1. **8 个 action**：stats / list / detail / createBatch / createWaybill / markPrinted / cancel / trace
2. **3 个集合**：merchants / orders / import_batches
3. **3 层幂等**：表内 Set → 库内查询 → 唯一索引
4. **并发**：写库 20 条一批，调外部接口串行
5. **超时**：3 秒 → 20 秒
6. **分页 bug**：页码要跟"加载成功"绑定，不是跟"翻页动作"绑定
7. **鉴权**：openid 只从服务端取
8. **面单**：适配层 + 环境变量切实现，不写死任何一家参数
9. **条码**：不能画假的，必须服务商返回
10. **最大亮点**：知道什么不该硬做（打印）、什么不能糊弄（条码）
